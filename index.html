The Access Lab

An experiential introduction to digital accessibility: Explore how presenting the same information in different ways impacts who can and can’t access it.

Note: Some of the activities below intentionally demonstrate inaccessible content as part of the lesson. Everything outside those activities aims to meet WCAG 2.1 AA standards or better.

What this reveals

The text was always there, styled white on white. A screen reader reads it aloud, and anyone who knows where to look can copy it to the clipboard. Sighted readers have no way to see it.

White on white is an extreme. Color contrast is a spectrum, and the same combination reads differently depending on text size, screen settings, viewing conditions, and who’s reading. A ratio that works on one screen may fall apart on another.

Key ideas

  • Everyone experiences information differently.
  • Context shapes how we perceive information. Small, low-contrast text may be readable up close and unreadable from across the room.
  • We all do accessibility work every day. Choosing fonts, colors, and layouts means making decisions about who can read what we create.
  • Our sense of what is and is not "readable" is calibrated to how we personally experience information.
  • Developing an accessibility practice means understanding the range of ways people interact with information.

1

Try to copy the hours.

✗ We can’t select or copy text from an image. The text would need to be retyped manually.
✓ Hours copied to clipboard.
2

Try a screen reader on this page.

🔊 Screen reader announces
“Image.”

Without a text layer, a screen reader can only announce the element type — not what the content shows.

3

Compare: switch to a version with a real text layer.

What this reveals

Both versions look identical on screen. When someone tries to listen, copy the hours to their calendar, or search for “Saturday” on the page, the image version has nothing to offer. A screen reader announces only “Image.” because the document contains no readable text.

Scanning or screenshotting text and saving it as an image removes other ways of interacting with the content beyond looking at it.

Key ideas

  • When we scan or screenshot text into an image, we remove all interactive and auditory access.
  • Alt text gives screen reader users something to hear. Copy/paste and search still require a real text layer.
  • Real text supports listening, copying, and searching. An image file supports only visual access.

Navigate using only your keyboard. Press Tab and Shift+Tab to move, Enter to select. Try to reach the Holiday closures button.

Click somewhere neutral first to clear focus, then Tab in.

2

Found a dead end? See what’s happening under the hood.

“Library events” is a real <button> — naturally focusable, keyboard-activatable. “Holiday closures” is a <div> with an onclick. This is a common pattern that looks identical on screen but is invisible to keyboard navigation.

What this reveals

Both seeing and listening to the information works in this example. Even so, “Holiday closures,” which looks like a button, and acts like a button if you click on it, is not encoded as a button. That means that tab navigation moves right past it. Mouse users will be able to access the information, but keyboard users will not.

The hours block has a label that looks like a heading. It uses the same font size and weight as other headings on the site. But it is encoded as a heading. Screen reader users who navigate by headings to skim a page will skip right past it.

The take-away here is that visual styling does not create document structure.

Changing how the heading and the button are encoded are small fixes in the code. For a keyboard user, changing how the button is encoded makes the difference between reaching an option and not knowing it was there. For a screen reader user, encoding the heading as a heading ensures it is properly announced and makes the page more navigable.

Key ideas

  • Changing <div> to <button> is a one-word fix. For a keyboard user, that word determines whether an option is reachable at all.
  • Heading-like styling does not create heading structure. A screen reader user navigating by headings will not find a paragraph styled to look like one.
  • Headings give screen reader users a way to navigate by structure. An hours block with no heading falls outside that path.
  • Mouse users often discover these barriers only when they need to complete a task without one.

The reframe

All of our digital work already involves thinking about accessibility. When we choose a font size, a color combination, or a file format, we’re making decisions that shape who can access that information.

Those decisions are often shaped by how we personally interact with the world, and by what we expect others will do too. That’s a reasonable starting point.

The next stage of accessibility work builds on what we’re already doing: developing the habit of asking, for each choice we make, how can I make this information accessible for people who experience and interact with information in different ways than I do.

For library workers specifically

A library’s mission is information access. When we choose whether to include alt text, use real text over a scan, or mark up a button correctly, we’re deciding which patrons that mission actually reaches. Accessibility work and information access work are the same work.

Key standards

WCAG stands for Web Content Accessibility Guidelines, the international standard for digital accessibility developed by the World Wide Web Consortium. Each guideline is assigned a conformance level. Level A sets the baseline; AA is the standard most organizations aim for and the one most legal frameworks reference; AAA covers additional criteria that apply to specific content types and contexts.

In these activities, we covered concepts related to the following WCAG criteria:

Criterion Level What it requires Demonstrated in
1.4.3 Contrast (Minimum) AA 4.5:1 ratio for normal text; 3:1 for large text Activity 1
1.4.6 Contrast (Enhanced) AAA 7:1 ratio for normal text Activity 1
1.1.1 Non-text Content A All non-text content has a text alternative (alt text) Activity 2
1.4.5 Images of Text AA Use real text instead of images of text when possible Activity 2
2.1.1 Keyboard A All functionality is available from a keyboard Activity 3
4.1.2 Name, Role, Value A UI components must expose name, role, and state to assistive technologies Activity 3

These six criteria cover what came up in the activities. The full WCAG 2.1 specification includes 78 success criteria across all three levels.
