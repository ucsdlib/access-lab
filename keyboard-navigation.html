Keyboard Navigation

Navigate a library services widget using only your keyboard, and discover why some options are reachable and others are not.

This activity contains one intentionally inaccessible element. That element is the lesson.

Found a dead end? See what’s happening in the code.

“Reserve a study room” and “Ask a librarian” are real <button> elements — naturally focusable and keyboard-activatable. “Interlibrary loan” is a <div> with an onclick. It looks identical on screen but is invisible to keyboard navigation.

What this reveals

You can see all three options. Tab reaches “Reserve a study room” and “Ask a librarian.” “Interlibrary loan” is skipped entirely. Without a mouse, there is no way to reach it.

This happens because “Interlibrary loan” is a <div> element with an onclick handler. Unlike <button>, a <div> is not in the keyboard focus sequence by default. Screen readers also cannot announce it as an interactive control.

Changing <div> to <button> is one word in the code. For a keyboard user, that word determines whether a library service is reachable.

Key ideas

  • Keyboard-only navigation is the baseline test for most assistive technologies. If Tab cannot reach it, the option is effectively invisible.
  • A <div onclick> looks and behaves like a button for mouse users. For keyboard and screen reader users, it does not exist as an interactive element.
  • One word in the code (div → button) opens or closes access to a library service for every patron who navigates without a mouse.
  • 26% of people with disabilities rely on some form of keyboard-based navigation. Keyboard accessibility is not an edge case.

Key standards

WCAG (Web Content Accessibility Guidelines) is the international standard for digital accessibility. Each success criterion is assigned a conformance level: A is the baseline, AA is what most organizations target, and AAA covers enhanced requirements. This activity covered two WCAG criteria:

Criterion Level What it requires
2.1.1 Keyboard A All functionality is available from a keyboard
4.1.2 Name, Role, Value A UI components must expose name, role, and state to assistive technologies

The full WCAG 2.1 specification includes 78 success criteria across all three levels.
